CLO-3: Server-side technologies for secure database interactions

Q-a) How this logic would shift to PHP + MySQL

In our current project we store everything in the browser's LocalStorage. If we move to PHP + MySQL the flow changes like this:

  • Frontend stays the same — HTML forms still collect username, password, skills, etc.
  • Form data is sent to PHP — Instead of saving to LocalStorage, the form submits (or uses fetch()) to a PHP file on the server, e.g. signup.php.
  • PHP processes the data — The PHP script receives the data with $_POST, validates it, hashes the password with password_hash(), and runs an SQL query to insert it into a MySQL table.
  • Login check — On login, PHP fetches the user row from MySQL and uses password_verify() to compare the entered password against the stored hash.
  • Session management — PHP uses session_start() and $_SESSION to keep users logged in across pages, instead of checking LocalStorage.

Example PHP signup snippet:

// signup.php
$username = $_POST['username'];
$password = password_hash($_POST['password'], PASSWORD_DEFAULT);

$sql = "INSERT INTO users (username, password) VALUES (?, ?)";
$stmt = $conn->prepare($sql);
$stmt->bind_param("ss", $username, $password);
$stmt->execute();

Q-b) CRUD Operations at Server Side

CRUD stands for Create, Read, Update, Delete — the four basic operations on any data. Here is how each maps to SQL and a real example:

  • Create — INSERT INTO skills (name, user_id) VALUES (?, ?) — Adds a new skill.
  • Read — SELECT * FROM skills WHERE user_id = ? — Gets all skills of a user.
  • Update — UPDATE skills SET name = ? WHERE id = ? — Edits an existing skill.
  • Delete — DELETE FROM skills WHERE id = ? — Removes a skill.

In our project, we simulate CRUD with LocalStorage arrays (push = Create, read array = Read, splice = Delete). On a real server, each operation becomes an SQL query executed by PHP.

Q-c) Importance of Server-Side Authentication

Server-side authentication is critical because:

  • Security — Client-side checks (like our JS validation) can be bypassed by anyone using browser DevTools. Server-side code cannot be seen or changed by the user.
  • Password safety — Servers hash passwords before storing them. LocalStorage stores data in plain text that anyone on the device can read.
  • Session control — The server can create and destroy sessions, enforce timeouts, and block unauthorized access to pages.
  • Data integrity — Only the server should decide whether data is valid before writing to the database, preventing malicious or corrupted input.
  • Multi-device access — Server auth lets users log in from any device, while LocalStorage is limited to a single browser on a single device.

Conclusion: LocalStorage is useful for demos and prototyping (like this assignment), but a real-world portfolio website must use a server-side database for security, reliability, and multi-device access.
